3 Architectural Approaches

How should the AI orchestration layer connect to ERPNext?

A

Predefined Tool Calling

The LLM is given a fixed set of Python functions ("tools") that map to ERPNext API calls — create_customer, query_sales, configure_module, etc. User chats → LLM picks which tools to call → results returned.

Pros

  • Predictable, safe, testable
  • Easy to audit what the AI can do
  • Works well with smaller LLMs like Qwen

Cons

  • Limited to predefined capabilities
  • New features require new tool functions

⭐ Recommended

B

RAG + Tool Calling Hybrid

ERPNext data is indexed into a vector store (e.g. ChromaDB). Queries search the index first ("what are my top customers?"), while actions still use tool calling. Two-track system: read via RAG, write via tools.

Pros

  • Better at answering complex data questions
  • Handles large datasets without hitting token limits

Cons

  • More complex — needs vector DB
  • Index must stay in sync with ERPNext data
C

LLM-Generated API Calls

The LLM is shown the ERPNext API schema and generates raw API calls dynamically. More flexible — can technically do anything ERPNext supports without pre-coding each operation.

Pros

  • Maximum flexibility
  • No need to pre-define every operation

Cons

  • Risky — LLM can make unintended API calls
  • Harder to test and audit
  • Unreliable with smaller/local models
